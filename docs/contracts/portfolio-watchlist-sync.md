# Automatic portfolio watchlist revisions

This repair protects automatic research-list maintenance. It does not qualify
alpha rankings, reconcile the account, grant sizing authority or execute trades.
The original complete source and three invented failure cases are retained in
`tests/fixtures/pre-snapshot-sync/`. Actual private packets are not acceptance data.

## Source requirements

The complete alpha object must have a nonempty identified universe, matching
integer total/scored/tier counts, unique string symbols, a model version, finite
0–100 scores and the producer's consistent ordered ranks and tier thresholds.
An empty, missing, malformed or all-unscored universe cannot clear existing rows.
A valid nonempty universe with no S/A candidates can remove prior automatic rows.
Source order and the existing ten S / fifteen A limits are preserved.

The alpha clock must be within three hours, and its original screener clock within
120 hours, with a five-minute future tolerance. These are explicit operational
age policies for the existing hourly path, not verified observation freshness or
point-in-time qualification. Explicit source quality other than `fresh` is
ineligible. Unknown timestamps never become the current time. Complete finite
JSON is hashed and identified in the sync diagnostics; the hash alone does not
prove an archived original source exists.

The four existing sidecar reads now require the complete declared byte length,
actual EOF, strict UTF-8 and JSON without duplicate members, nonfinite values or
lone surrogates. A 32 MiB bound and twenty-second acceptance deadline apply;
the deadline does not override the SDK socket timeout. Bodies are closed. A read
failure remains unavailable and cannot become an empty eligible universe.

## Atomic owner protection and revision ordering

The engine strongly reads the whole paginated watchlist and its checkpoint in
the existing table. Manual and unrecognized ownership are protected. Automatic
updates preserve the original notes, added date and other metadata; absent source
metadata is not relabeled manual in the snapshot.

One DynamoDB transaction includes the checkpoint and every intended automatic
row mutation. Each affected old row must still match all observed attributes and
the presence/absence of standard owner-edit attributes. A new row must still be
absent. New arbitrary fields added concurrently by an external writer are not a
general item-version guarantee; recognized manual conversions and notes edits
are explicitly guarded. The checkpoint condition orders automatic writers, so
an older source cannot overwrite a later committed revision. Equal timestamps
with different complete-source hashes are rejected; an identical committed
revision is idempotent and does not resurrect a subsequently removed row.

The complete request must fit 100 actions and the conservative 3.5 MB encoded
request bound. Larger lists are withheld, never truncated or split into partial
transactions. DynamoDB also enforces its item/transaction size and expression
limits. A condition conflict applies none of the automatic changes. This follows
the [DynamoDB transaction contract](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_TransactWriteItems.html).

An explicit successful SDK HTTP acknowledgement is required to report `APPLIED`.
An ambiguous transport result reports `WRITE_UNCONFIRMED`, with no claimed
added/removed rows. No immediate application retry occurs. The next original
scheduled run can recognize an already committed checkpoint. A service
permission or preparation failure never falls back to unconditional writes.
The checkpoint is operational state, not a new account, research ledger or
acceptance-data source.

## Page and release evidence

`watchlist_sync.schema_version` is `watchlist-sync.v1`. The page separates applied,
unchanged, withheld, conflict, uncertain and unavailable legacy states. It retains
all supplied watchlist rows, source dates and explicit research-only language.

Only this function can select `offline_snapshot_v1` in its release configuration.
The release helper verifies every file and byte in the exact built ZIP against
reviewed source, rejects extra/missing/duplicate members, runs the actual current
80-case invented suite plus four handler checks, and rechecks the package after
testing. The child receives no runner/provider credentials; networking and
subprocess audit hooks refuse external activity. No native validation invocation
occurs. Existing version/hash pins, alias compare-and-swap, schedule preservation
and rollback remain active. Other functions keep their existing validation mode;
unknown modes fail rather than falling back to invocation. Snapshot ZIPs exclude
interpreter caches generated by tests.

The former `validate_only` handler is not a private-data-free acceptance method:
it reads the normal input sources. Do not invoke it for this repair. Acceptance
uses the exact release receipt and complete native package, unchanged original
resources and both hourly :40 bindings, plus static bytes and isolated browser
fixtures. Normal private publication, actual table IAM execution, independently
verified marks, account reconciliation and investment performance remain
unverified. Snapshot publication ordering and the remaining valuation issues
require separate repairs.
