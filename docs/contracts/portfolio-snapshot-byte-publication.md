# Bounded snapshot serialization and acknowledgement

The snapshot validates the complete existing typed binary64 value contract before preparing any publication. It then creates its compact JSON body once, with the same ASCII escaping, field order and finite number formatting as its preceding S3 representation. Strings are escaped in bounded chunks and the complete 20,000,000-byte limit is checked before each buffer write. No field, record, source body or numeric precision is discarded to fit.

The same immutable bytes are supplied to the authenticated mirror request and S3. Before S3 is written, the mirror must acknowledge `portfolio-snapshot-bytes.v1`, the exact full-body SHA-256, its byte count and the complete typed identity size. `ok: true` alone is insufficient. The publisher rejects redirects, an unexpected origin or final URL, non-200 responses, ambiguous headers, non-identity content encoding, invalid or incomplete JSON, duplicate acknowledgement fields and mismatched acknowledgement values.

Acknowledgement reads are bounded to 4 KiB. The acceptance window is at most 25 seconds, each socket timeout at most eight seconds, and the current Lambda time budget retains five seconds for S3. Missing or insufficient budget refuses publication before requesting credentials or starting transport. Expiry after a request means the mirror write is unconfirmed; it does not establish that no write occurred. Blocking runtime calls can exceed an acceptance deadline, so this is not a hard process deadline guarantee.

Deployment checks the exact already-shipped Worker receipt, retained complete source capture and repository build inputs before changing the native function. It also checks the existing snapshot origin configuration without logging environment values. Snapshot and risk have separate explicit prerequisites; other native consumers are not opted into this protocol. Native resource limits, roles, bindings and schedules remain unchanged.

The prerequisite commit is the retained Worker **release** commit. An identical-code redeployment can issue a new receipt without a source edit. The gate requires that release to be an ancestor of the deployment checkout, compares the complete build inventory and every input at both commits, and requires unchanged committed receipt/capture evidence. It then requires the live receipt to equal that exact retained receipt. It does not substitute the last source-edit commit, accept arbitrary newer releases, or waive a source mismatch. Worker test-only dispatch selection still needs a separate correction; this gate remains safe when identical bytes are redeployed.

This is still two separate destination writes. A failure after the mirror acknowledges its write can leave S3 on its predecessor. The function reports failure rather than claiming a successful snapshot. No automatic retry, rollback, concurrent-publication ordering, strongly consistent KV read or atomic commit is invented. Those recovery and ordering questions remain open.

Checks execute current source with complete invented inputs and mocked transport/storage. Full native output bodies are checked against the exact preceding compact encoding. Negative zero, Unicode, record completeness, consumer identity limits, failure paths, runtime reserve and secret-safe diagnostics are exercised. Whole predecessor source and bad acknowledgements remain inert, hash-bound evidence. Candidate ZIP validation uses all packaged source files and runs offline without credentials or network access. Native acceptance reads only selected release receipts and code/configuration metadata; it never reads an actual account packet or invokes a producer.

Measured local Python allocation reductions describe the serializer's incremental allocations only. They are not a measurement of total Lambda memory or an investment-quality certification. Actual private publication, consistent book acquisition, source qualification and supported portfolio decisions remain separate requirements.
