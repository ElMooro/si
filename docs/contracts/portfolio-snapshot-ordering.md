# Ordered snapshot publication

The snapshot mirror has a dedicated object in the existing `WORKSPACE_COORDINATOR` namespace. It uses the existing owner/service authorization boundary. Only the service publisher can reserve a revision or write a packet; owner reads remain private and uncached. There is no new namespace, binding, schedule, native runtime configuration, credential or provider request in this change.

`POST /private-artifact?kind=portfolio-snapshot&action=reserve` issues an increasing integer revision and a random reservation token. The producer must reserve before acquiring its book and research inputs. The revision therefore expresses acquisition-attempt order, not completion time, investment confidence or market observation time. The reservation journal retains 128 issued reservations. An expired candidate is refused rather than given a new rank after collection.

An ordered body adds `publication: {schema_version: "portfolio-snapshot-publication.v1", revision, started_at}`. Its request carries the reservation token and complete body SHA-256. The token is not part of the stored document. The entire body must satisfy the existing strict UTF-8/JSON, finite safe-number, depth, 20,000,000-byte and 32 MiB typed-identity limits. Original formatting, negative zero, unknown fields, records and retained source bodies are preserved.

The object serializes requests through external awaits as well as storage operations. Its transaction writes 256 KiB body chunks and the current pointer together. A newer accepted revision rejects older arrivals. An identical token, revision and body can be retried without replacement; conflicting bytes at the same revision are refused. Reads reconstruct every chunk, verify the full digest and typed identity, and check that the stored publication metadata agrees with the current pointer. Missing or corrupt state fails rather than falling back to a stale copy.

Before the first ordered write, the existing unnumbered native publisher remains compatible: it receives the existing `portfolio-snapshot-bytes.v1` acknowledgement and stores the original bytes in private KV. This compatibility mode does **not** provide ordering. First activation retains the whole valid pre-migration KV body in the object. It never overwrites or deletes that migration predecessor. Once ordered publication begins, unnumbered writes are rejected and reads use the ordered object even if an old Worker writes to KV later. An invalid predecessor prevents migration without replacing it.

The acknowledgement binds protocol, revision, complete body hash/length and typed identity size. The object retains current and the migration predecessor. Retention of each subsequent prior S3 packet is the native publisher's responsibility; it is not supplied by this mirror change.

The Worker must ship and its complete control-plane source/configuration capture must match the reviewed build before the native publisher uses the protocol. Worker test-only pushes run tests without redeploying code or issuing a replacement receipt. Workflow/evidence-tool changes select the governed data proxy, including when the same push changes a second Worker.

Native reservation, conditional S3 publication, complete prior-packet archival and recovery across the two stores remain a subsequent step. These stores are not one atomic transaction. This Worker release alone cannot establish ordered end-to-end publication or successful actual account delivery. Acceptance uses complete invented bodies, current handlers/modules, local workerd/SQLite and exact control-plane release evidence. It never inspects an actual private packet or invokes a live producer.

Native cutover must also prevent the preceding unconditional S3 writer from replacing a newer body: an invocation can remain in flight after code promotion. A conditional new writer alone cannot fence an old unconditional writer. The existing bucket policy and all callers must be reviewed before selecting the cutover control; no policy change or drain guarantee is implemented by this Worker prerequisite.
